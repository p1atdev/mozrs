# 検証記録

2026-10-25、Linux x86_64 上で実行。
上流は `c4b2aef7c65e61be394bacadaec200eb5b97f91c` に固定。
Rust 1.99.1、Bazel 9.0.2、Python 3.12.14 を使用した。

## 実行結果

| 対象 | 全件復号した読み数 | トークン数 | C++ と比較した入力数 | 不一致 |
|---|---:|---:|---:|---:|
| 合成辞書 | 315 | 620 | 1,268 | 0 |
| 上流テスト辞書 | 30,153 | 65,744 | 4,014 | 0 |
| 上流 OSS 辞書 | 889,345 | 1,436,931 | 4,014 | 0 |
| Rust 生成の前処理合成辞書 | 78 | 281 | 170 | 0 |
| Rust 生成の OSS 辞書 | 889,345 | 1,436,931 | 4,014 | 0 |

比較は同一バイナリを上流 C++ `SystemDictionary` と Rust で読み、読み・表記・
コスト・左右品詞 ID・属性・件数・返却順を照合した。候補をソートしたり、
重複を除去したりしていない。C++ 辞書実装のソースは変更していない。

実辞書の各検索モードは固定 seed `20261025` による 2,000 読みと追加 7 入力。
共通接頭辞検索では非空の読みの後ろに「です」を付けた。
抽出元はテスト辞書の `dictionary.txt` と OSS の `dictionary00.txt`〜`dictionary09.txt`。
生成辞書にはそれ以外の補助・手動追加データも入るが、全読みの C++ 比較ではない。
Rust 生成 OSS の追加比較は、補助語彙・郵便番号を含むフィルター済み語彙・domain.txt
から抽出した 2,000 読みと追加 7 入力を各モードで使用した。
前処理合成辞書は全 78 読みと追加 7 入力を両モードで比較した。

| 辞書 / モード | 入力数 | 比較した返却トークン数 |
|---|---:|---:|
| テスト / 完全一致 | 2,007 | 4,319 |
| テスト / 共通接頭辞 | 2,007 | 34,368 |
| OSS / 完全一致 | 2,007 | 3,375 |
| OSS / 共通接頭辞 | 2,007 | 106,512 |
| Rust 生成前処理合成 / 完全一致 | 85 | 284 |
| Rust 生成前処理合成 / 共通接頭辞 | 85 | 296 |
| Rust 生成 OSS / 完全一致 | 2,007 | 3,158 |
| Rust 生成 OSS / 共通接頭辞 | 2,007 | 90,928 |

`cargo fmt --check`、`cargo clippy --locked --offline --all-targets -- -D warnings`、
`cargo test --locked --offline` が成功。Rust のテストは計 **17 件**。
合成辞書の 1,268 ケースはそのうち一つのテスト内で全件比較した。

不正入力については、6,704 バイトの合成辞書の全切断位置、コンテナ・内部
インデックス・最初のトークンの破損、非正規の Unicode 符号、2,000 通りの
決定的な変異を確認した。有効な別データになる変異は必ずしもエラーにならない。
CLI の JSON エスケープ、空入力、CRLF を含む標準入力、異常終了も確認した。

## Rust 辞書生成の検証

以下は検索結果だけでなく、生成ファイルを全バイト照合して一致した。

| 入力 | Rust / C++ 生成物の大きさ | 結果 |
|---|---:|---|
| 元の合成 620 トークン（コスト圧縮閾値 1） | 6,704 byte | バイト一致 |
| 合成 TSV + 品詞定義 + 読み補正（閾値 6） | 2,500 byte | バイト一致 |
| OSS 原データからの通常生成（閾値 6） | 14,651,852 byte | バイト一致 |

合成 TSV は手書きの 20 行と上流の濁点正規化表の全 258 規則。
C++ `TextDictionaryLoader` が出力した未圧縮の 281 トークンとも、Rust の処理結果を
順序込みで照合した。ZIP_CODE / ENGLISH の品詞、正規化、同コストでの品詞の選択、
重複補正、既存読み・存在しない表記のスキップ、補正語の属性とコストを含む。

通常生成は `tools/build_oss.py` で独立して実行した。郵便番号・補助語彙・フィルター
結果の中間ファイルも上流 Bazel 生成物と全バイト一致。初回検証で見つかった
入力順の差は、上流のファイル展開順（郵便番号が先頭）に合わせて解消した。
通常生成で Mozc C++・Bazel・user_pos_manager.data を使用していない。

生成側のテストでは、空辞書、かな表記だけの辞書、256 byte の最大深さ、圧縮可能な
コストと同音・多読による圧縮抑制も確認。不正な数値・品詞 ID・属性、空の語・NUL・
長すぎる語、読み補正のコスト溢れ、不正 UTF-8、CLI のエラー時に既存出力を保持する
ことを確認した。これらの異常系・最大深さの全ケースを C++ でも実行したわけではない。

既定設定で意図した語彙・順序・形式の差はない。上流と同じ条件でコストの下位 8 bit
を捨てるため、復号コストが未圧縮の入力コストと異なる場合はある。
入力の扱いでは、固定長バッファの範囲外となる語、NUL、不正な値などを Rust の
エラーとして拒否する。C++ の CHECK による終了や、範囲外入力の挙動を再現する目的はない。
小コスト圧縮の設定を変えた生成物は、既定の上流生成物とのバイト一致の対象外。

## 再現と識別子

```sh
python3 tools/validate.py --bazelisk /path/to/bazelisk
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

C++ を使わない通常生成だけなら `python3 tools/build_oss.py`。
実行環境では既存キャッシュを共有するため、両スクリプトに
`--cache /workspace/shared/mozc-port` を指定した。

比較入力・C++/Rust 出力・ビルドログ・`report.json` はローカルの
`validation-output/` に保存される。
上流アーカイブは SHA-256 検証し、展開済みファイルもアーカイブと照合する。

| 合成辞書 | `3973fec8a841650ddcd461b2a3a1374cda50f63c86f6e6527a48755eb43b789f` |
| 合成辞書の C++ 期待値 | `d52113f81d6250a8a368d5d65784f1c34d8fadade805d4faf2c2380a4def4d14` |

`manifest.json` に記録。検証時に作った Rust 生成辞書の記録は
`validation-output/rust-oss/manifest.json` にある。

## 検証の限界

完全なかな漢字変換、予測、学習、IME 統合、異なる上流版、他 OS、宣言した
最小 Rust 版でのビルドは未検証。速度とメモリの比較測定は行っていない。
実データの生成バイト一致は今回の固定入力に対する結果であり、任意の将来データでの
一致を保証しない。全件復号の成功は全読みを C++ と検索比較したことを意味しない。変異テストも網羅的な
fuzzing や資源消費上限の証明ではない。
